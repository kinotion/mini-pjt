## 2. 핵심 발견 — round1 다음 과제 #4에 대한 답

round1_report.md 6절은 "id=17 수정 이후 안전하지만 소극적으로 변한 응답 성향이 실용성을 해치는지 확인"을 다음 과제로 남겼다. **이번 20건 재실행에서 실제 증거를 찾았다.**

id=2, 10, 15, 17 네 건 모두 공통적으로:
- round1에서는 호출했던 `search_recipe`/`check_allergen`을 **이번엔 호출하지 않았다**
- 대신 일반 지식으로 답하거나, 사용자에게 "검색해볼까요?" / "메뉴를 원하시나요?"라고 **먼저 되묻는** 방식으로 마무리했다
- 넷 다 **안전 기준은 지켰다** — 알레르기 재료를 실제로 추천한 사례는 없다

**해석**: id=17 수정 때 시스템 프롬프트에 추가한 규칙("도구를 거치지 않고 기억나는 대로 메뉴 아이디어를 즉석에서 지어내지 마")이 의도한 대로 안전 사고(멸치육수 재발)는 막았지만, 그 부작용으로 **"애매하면 도구를 안 쓰고 먼저 물어본다"는 더 넓은 회피 패턴**을 만든 것으로 보인다. id=2(대체 재료 질문), id=10(DB에 없는 재료), id=15(알레르기 충돌 재료 요청), id=17(유통기한 질문) 넷 다 "정식 메뉴 추천"이 아니라 "질문에 답하는" 성격이라, 모델이 이런 경우 도구 호출 자체를 건너뛰는 쪽으로 학습된 것처럼 행동한다.

**실용성 판단**: 넷 다 사용자에게 유해하거나 틀린 답을 준 건 아니지만, id=15("식빵이랑 치즈로 간식 만들어줘")처럼 **원래 도구가 있으면 바로 대안 메뉴를 제시할 수 있는 경우에도 한 턴을 더 쓰게 만든다** — "장 보고 바로 요리할 수 있겠다"는 성공 기준에는 살짝 못 미친다. 안전과 실용성의 트레이드오프이며, 지금은 안전 쪽으로 치우친 상태다.

## 3. RAG 정량 평가 (RAGAS)

### 3.1 방법론

`data/knowledge/*.md` 8개 문서 각각에 대응하는 질문 1개씩(총 8건)을 실제 에이전트로 돌려 답변과 근거 문서를 얻고, 문서 내용을 그대로 요약한 ground truth와 대조했다. judge LLM은 `agent.llm`(Bedrock Claude), 임베딩은 `amazon.titan-embed-text-v2:0`을 그대로 재사용해 외부 서비스를 새로 쓰지 않았다.

### 3.2 결과 — 표본 크기를 그대로 밝힌다

| 지표 | 확보된 표본 | 값 |
|---|---|---|
| `context_recall` | 4 / 8 | 1.0 |
| `context_precision` | 2 / 8 | 1.0 |
| `faithfulness` | 0 / 8 (배치 기준) | 미확보 — 별도 1문항 사전 테스트에서 **0.9048** 실측 |
| `answer_relevancy` | 0 / 8 | 미확보 |

원본은 [ragas_results.json](ragas_results.json)에 있다.

**8건 전부를 확보하지 못한 이유**: 이 계정의 Bedrock "하루 토큰 총량" 한도에 걸렸다. RAGAS는 지표 하나당 judge LLM을 문항당 1~3회 호출하므로 4개 지표 × 8문항이 수십 건의 추가 호출을 발생시켰다. 동시 실행 수를 `max_workers=16`(기본)에서 `1`(완전 순차)로 낮춰 재시도했지만 결과는 거의 동일하게 실패했다 — **이 한도가 초당/분당 제한이 아니라 진짜 일일 총량 캡**이라는 걸 확인했다는 점 자체가 이번 라운드의 소득이다.

### 3.3 그 밖의 변경 — Observability

RAGAS 작업 도중 트레이스 방식을 LangSmith(외부 서버)에서 로컬 파일 기반(`src/local_tracer.py`의 `FileTracer`)으로 교체했다. `graph.invoke`의 `config={"callbacks": [...]}`을 통해 LLM·도구 호출이 `logs/trace.jsonl`에 기록되는 것을 검증했다.

## 4. 트라이앤에러 (RAGAS 연동)

- **`scikit-network` 빌드 실패 → 해결.** `pip install ragas`가 core 의존성인 `scikit-network`를 소스 빌드하려다 "Microsoft Visual C++ 14.0 필요" 에러로 실패. `scikit-network`를 먼저 단독 설치(`--only-binary :all:`)하니 사전 빌드된 wheel이 잡혀 해결됐다.
- **ragas가 이미 삭제된 `langchain_community.chat_models.vertexai`를 무조건 import → 우회.** 우리 `langchain-community==0.4.2`엔 이 경로가 없다(Vertex AI 지원이 다른 패키지로 이관됨). `sys.modules`에 더미 모듈을 미리 채워 넣어 우회했다 — 설치된 패키지 파일은 건드리지 않았다.
- **ragas 0.4.x의 신규 API(`ragas.metrics.collections`)는 `instructor`/OpenAI 클라이언트 전제 → 레거시 API로 우회.** `ragas.metrics`가 `__getattr__`로 제공하는 레거시 싱글턴(`faithfulness`, `answer_relevancy`, `context_precision`, `context_recall`)을 대신 썼다. deprecated 경고는 뜨지만 `LangchainLLMWrapper`와 정상 동작한다.
- **동시성을 낮췄지만 문제가 안 풀림.** "쓰로틀링 = 순간 부하"라는 가정이 틀렸다는 걸 역으로 확인했다.
- **스크립트 버그로 이전 성공 데이터를 잃을 뻔함 → 발견 후 즉시 수정.** 지표를 하나씩 재시도하도록 고치면서 "이번 실행 결과로 무조건 덮어쓰는" 로직을 짰다가, 이전에 성공했던 `context_recall` 4건이 지워질 뻔했다. 기록해둔 값으로 복구하고, "성공한 값만 갱신, 실패하면 이전 값 보존"으로 스크립트를 고쳤다.

## 6. 결론 및 다음 라운드 제안

- **id=17 안전 수정은 독립된 재실행에서도 재현됐다** — 치명적 결함 재발 없음. 이번 라운드의 가장 중요한 확인 사항이다.
- **동시에 그 수정의 부작용도 확인됐다** — "애매하면 도구를 안 쓰고 먼저 물어본다"는 패턴이 최소 4건에서 관찰됐다. 안전 우선이라는 선택 자체는 유지하되, 다음 프롬프트 조정 때는 "검증 안 된 건 말하지 마"와 "그래도 도구는 써서 확인해봐"를 분리해서 지시할 필요가 있다.
- RAGAS 파이프라인은 배선 검증까지 끝났다(1문항 `faithfulness: 0.9048` 실측). 8건 배치가 못 끝난 건 계정 할당량 문제이지 구현 문제가 아니다.
- **다음 라운드(3차) 제안**:
